# Подключение своего агента

Интеграция сообщает, что делает агент. si-notch показывает сессии, инструменты, прогресс, расход токенов и запросы внимания. Выполнение действий, учётные данные и политика разрешений остаются у агента.

Для большинства интеграций используйте встроенный CLI. Unix-сокет подходит для самостоятельного отправителя без зависимостей. Для Hermes уже есть [поддерживаемый плагин](../../plugins/hermes/README.ru.md); второй параллельный наблюдатель не нужен.

## Начало работы с CLI

Запустите si-notch и скопируйте путь helper из **Настройки → Диагностика**. Для стандартной установки:

```sh
SI_NOTCH_CLI=/Applications/si-notch.app/Contents/Helpers/si-notchctl
"$SI_NOTCH_CLI" paths
"$SI_NOTCH_CLI" status
"$SI_NOTCH_CLI" emit '{"event":"agent.working","session_id":"my-agent-machine1-chat1","provider":"my-agent","turn_id":"turn-1","id":"event-1","sequence":1,"title":"Проверка сборки","message":"Выполняются проверки"}'
"$SI_NOTCH_CLI" emit '{"event":"agent.completed","session_id":"my-agent-machine1-chat1","provider":"my-agent","turn_id":"turn-1","id":"event-2","sequence":2,"message":"Проверки пройдены"}'
```

Последние две команды создают и завершают настоящую локальную карточку. Передавайте текст только с учётом выбранных пользователем настроек приватности. JSON можно передать через stdin. `emit` возвращает ненулевой код при неверном вводе, отклонении, таймауте или разрыве соединения; ошибка наблюдателя не должна останавливать самого агента.

Команду без собственных хуков можно обернуть:

```sh
"$SI_NOTCH_CLI" run --agent my-agent --title "Проверки проекта" -- python3 -m unittest
```

`run` запускает процесс напрямую, сохраняет stdin/stdout/stderr и возвращает его код завершения. Он не видит внутренние инструменты, токены модели, подагентов и запросы разрешения. `hook`, `notify`, `harness-hook` адаптируют готовые форматы событий и не отвечают на запросы разрешения.

## Идентификаторы и порядок

| Поле | Контракт |
| --- | --- |
| `session_id` | Обязательный постоянный ID диалога/сессии. Добавляйте пространство имён агента, машины и профиля. В живом списке ID глобален: один ID у разных `provider` недопустим. |
| `provider` | Короткое имя своего агента, например `my-agent`. Не используйте `codex` или `pi`: расход этих интеграций берётся из их собственных журналов. |
| `turn_id` | ID одного пользовательского запроса. Один и тот же во всех событиях запроса; новый для следующего запроса в той же сессии. |
| `id` | Уникальный неизменяемый ID события. При неизвестном результате доставки наблюдения повторяйте тот же конверт с тем же ID. |
| `sequence` | Необязательное целое ≥0, строго растущее на протяжении всей сессии, в том числе после перезапуска отправителя. Если хранить счётчик нельзя, последовательно обходитеcь без него и отправляйте упорядоченные timestamps. |
| `timestamp` | Unix seconds или ISO 8601; по умолчанию время получения. Для отложенного расхода указывайте время самого события. |
| `connection_id`, `connection_name` | Постоянный ID профиля и его название. Название требует ID. Сохраняйте ID при обновлении; клону профиля на другой машине нужен новый. |

ID начинается с ASCII-буквы или цифры и содержит только буквы, цифры, `.`, `_`, `:`, `-`. Сессия, запрос пользователя, профиль и задача — до 256 байт UTF-8; ID события и запроса расхода — до 512; `provider` — до 64.

Живой reducer хранит ограниченный набор ID событий. Меньшие или равные sequence отклоняются; когда сравнимого sequence нет, отклоняется более старый timestamp. Это ограниченное подавление повторов, а не постоянная очередь. `session.start` не обнуляет порядок. События одной сессии отправляйте последовательно; разные сессии могут работать параллельно.

## Жизненный цикл, прогресс, внимание

Обычная последовательность:

```text
session.start → agent.working → tool.start → tool.finish → agent.completed
                       └────→ agent.waiting → agent.working
```

- `session.start` создаёт простаивающую сессию. Пока работы нет, она может отображаться только в Агентах.
- `agent.working` начинает или возобновляет работу. `tool.start`, `tool.finish`, `tool.failed` описывают инструмент через `tool_name`. Ошибка инструмента сама по себе не завершает весь запрос ошибкой.
- `agent.completed` завершает запрос, `agent.failed` сообщает его неудачу. Следующий запрос того же диалога может начаться с `agent.working`.
- `session.end` закрывает сессию. После явного закрытия для возобновления нужен `session.start`.
- `agent.waiting` сообщает ожидание. Добавляйте постоянный `attention_request_id` только для настоящего нерешённого вопроса человеку. Пока вопрос тот же, ID не меняется; после ответа отправьте `agent.working`. Ожидание модели или инструмента не является вопросом пользователю.
- `approval.request` без живого канала ответа лишь сообщает о необходимости решения. Ответить нужно в исходном агенте.
- `agent.presence` требует `connection_id` и обновляет доступность без создания задачи и без продления её прогресса. Свежесть присутствия — две минуты. Не имитируйте работу ради heartbeat.

Для измеримого прогресса отправляйте `task.update`; произвольного поля процентов нет:

```json
{"event":"task.update","session_id":"my-agent-machine1-chat1","provider":"my-agent","turn_id":"turn-1","task":{"id":"tests","title":"Выполнить проверки","status":"completed"}}
```

Статусы: `idle`, `working`, `waiting`, `approval`, `completed`, `failed`, `ended`. Для checklist значение `ended` удаляет пункт. Изменения пункта используют тот же ID. `subagent.start`/`subagent.end` принимают объект `subagent` с `id`, `name`, `status` и необязательными `sessionID`, `parentTurnID`. Два последних вложенных ключа записываются в camelCase. Дочерняя сессия отправляет собственные события и расход. Завершение родительского запроса не означает остановку всех фоновых детей.

Ограничения UTF-8: `title` — 512 байт; `message`, `first_prompt` — 16 384; `cwd` — 4 096. Передавайте короткие публичные статусы, а не словари аргументов, вывод инструмента и скрытые рассуждения. Дополнительные `model`, `reasoning_effort`, `terminal_bundle_id`, разрешённые `target_url` дополняют карточку. [Архитектура](architecture.md) описывает историю и ограничения навигации.

## Расход токенов без повторного учёта

На каждый завершённый API-вызов отправляйте числовую запись:

```json
{"event":"usage.update","session_id":"my-agent-machine1-chat1","provider":"my-agent","turn_id":"turn-1","id":"usage-event-1","usage":{"request_id":"provider-call-1","input_tokens":1200,"output_tokens":180,"cached_input_tokens":800,"cache_write_input_tokens":0,"reasoning_output_tokens":40,"started_at":1792700000,"ended_at":1792700002}}
```

Всего здесь **1 380** токенов. Чтение и запись cache уже входят в input, reasoning уже входит в output. Нормализуйте счётчики провайдера к этому правилу один раз. Счётчики — целые ≥0; timestamps — конечные Unix seconds. Неизвестное поле пропускайте, не подставляйте выдуманный ноль. Для числовой записи постоянного журнала Usage нужны оба поля `input_tokens` и `output_tokens`.

`usage.request_id` обозначает один неизменяемый API-вызов внутри provider/connection/session. При повторной доставке ID и числа сохраняются. Конфликтующая запись с тем же ID отмечает данные как неполные, а не добавляет ещё один вызов. Для ребёнка передайте `usage.parent_session_id`, `usage.parent_turn_id` и его собственный `turn_id` в конверте. Это привязывает вклад к правильному родительскому запросу. При потере записей укажите `usage.incomplete:true`. Не включайте суммарный расход семьи в собственные счётчики родителя.

Удалять запись из очереди можно только после `{"ok":true,"disposition":"usage_committed"}`. Этот путь сохраняет журнал Usage и не меняет живую карточку. Обычного `ok:true` недостаточно; CLI и переносимый relay проверяют нужное подтверждение. Ограниченная приватная очередь может повторно доставлять неизменяемые числовые записи после восстановления связи. Потеря телеметрии не является причиной повторять запрос к модели.

Без `usage.request_id` числа считаются накопительным снимком и заменяют предыдущий снимок. Для одной своей сессии выберите снимки **или** отдельные записи вызовов: их смешивание может задвоить расход. Снимки не позволяют точно разнести расход по запросам. Для Codex/Pi источником истины являются локальные журналы, дополнительные счётчики событий не суммируются. Лимиты аккаунта — отдельная интеграция Codex, а не пересчёт локальных токенов и не универсальный billing API.

## Настоящие решения и вопросы

`request` предназначен для отправителя, который умеет остановить действие и применить решение:

```sh
"$SI_NOTCH_CLI" request '{"session_id":"my-agent-machine1-chat1","provider":"my-agent","turn_id":"turn-2","request_id":"permission-2","approval_id":"permission-2","message":"Разрешить эту одну команду сборки?"}' --timeout 60
```

Команда печатает JSON. Код **0** — разрешение или непустой ответ, **1** — отказ, **2** — неверный ввод, недоступность, таймаут или другая ошибка. Проверяйте JSON вместе с кодом выхода. Ответ разрешения содержит `ok`, `decision` (`allow`/`deny`), точный `request_id`. С `"question":true` показывается вопрос с текстовым вводом; успешный ответ содержит `decision:"answer"` и `answer`. Общий socket API не предоставляет произвольные списки вариантов или постоянные разрешения из Desktop-адаптера.

ID запроса — 1–160 ASCII-букв/цифр/`._:-`; каждой отдельной ожидающей операции нужен новый ID. Ответ связан с текущим соединением и сроком ожидания. Приложение поддерживает восемь ожидающих запросов, не более одного на сессию. `--timeout` — 0.1–110 секунд, по умолчанию 60. Новый запрос может отменить предыдущий. При отказе, отмене, таймауте, несовпадении ID или разрыве не выполняйте защищённое действие: вернитесь в родной интерфейс разрешения либо отмените операцию. Не повторяйте решение с неизвестным результатом. После решения отправьте фактическое следующее событие; приложение не выполняет действие за агента.

## Прямой Unix IPC

Сокет по умолчанию — `~/.si-notch/run/events.sock`. `SI_NOTCH_SOCKET` или `--socket` выбирают другой абсолютный путь; приложение и отправитель должны использовать один endpoint. Режим сокета — 0600, родительского каталога — 0700, владелец — тот же пользователь. Встроенный transport также проверяет небезопасных предков и симлинки. TCP endpoint и токена аутентификации нет.

Для каждого сообщения открывайте отдельное соединение `AF_UNIX`/`SOCK_STREAM`. Отправьте один компактный объект JSON UTF-8 и `\n`, прочтите одну строку JSON, закройте соединение. Не отправляйте несколько событий в одном соединении. Лимит канала — **128 KiB**, хотя основной parser допускает больший конверт. Ограничивайте время connect/read/write; учитывайте небольшой предел длины Unix socket path.

Обычное подтверждение содержит `ok` и `disposition`: `applied`, `duplicate`, `outOfOrder`, `ignoredUnknown`, `invalid` или `filtered`. Даже `ok:true` может подтверждать проигнорированное наблюдение; оно не доказывает изменение карточки. `status` — диагностика живых receipts, не стабильный поток подписки. Прямой запрос решения дополнительно задаёт `await_response:true`, `request_id`, `response_timeout` и при необходимости `question:true`.

## Рабочий пример и изолированные проверки

[`agent.py`](../examples/custom-agent/agent.py) использует только стандартную библиотеку Python 3.10+. Он показывает lifecycle, checklist, инструмент, расход отдельного вызова и необязательный вопрос. Числа токенов в нём учебные. Нужен явно переданный сокет; ответы не исполняются.

```sh
python3 docs/examples/custom-agent/test_agent.py
```

Проверки создают временный приватный Unix-сокет: полный запуск, повторная доставка, подтверждение сохранённого расхода, привязка ответа, отказ/разрыв, таймаут, права и macOS ACK/close race. Приложение, учётная запись, модель и настоящий агент не нужны. Если системный sandbox запрещает bind, этому изолированному процессу нужно разрешить временный локальный сокет.

Чтобы показать пример в запущенном приложении, явно выберите его endpoint:

```sh
python3 docs/examples/custom-agent/agent.py --socket "$HOME/.si-notch/run/events.sock"
# Добавьте --ask для одного вопроса с текстовым ответом.
```

Для SSH используйте самостоятельный [`plugins/hermes/relay.py`](../../plugins/hermes/relay.py) и [руководство по подключениям](remote-connections.md). `scripts/remote-relay.py` — обёртка репозитория, её нельзя переносить отдельно. Relay поддерживает `emit`, `hook`, `notify`, `request`, но не весь macOS CLI.

## Диагностика и удаление

Проверьте `paths`, `status`, endpoint, права и **Настройки → Диагностика**. «Установлен/настроен» отличается от «события получены». После подключения начните новый запрос. Для отсутствующей карточки проверьте disposition, коллизию ID, сброс sequence, фильтр завершённых, паузу и скрытых провайдеров. Для расхода — оба счётчика, постоянные ID вызовов и `usage_committed`.

Удаление своей интеграции означает удаление только её регистрации хука/плагина и остановку её worker. Сохраняйте чужие настройки и хуки. SSH-туннель приложения отключается отдельно. Удаление наблюдателя не стирает локальные History и Usage; для удаления сохранённых данных используйте соответствующие средства приложения.
